Trigger on requests to add JWT auth, fix a "logout doesn't actually invalidate the session" bug, or decide between cookie and localStorage token storage.

Designing JWT-based session management for a production auth system. Most of the damage here comes from treating a JWT like a session token when it structurally isn't one.

Non-negotiables:

- **Access token lifetime: 5-15 minutes. Refresh token: days to weeks, with rotation.** A long-lived access token is a long-lived unrevocable credential (see below) — the blast radius of a stolen one is bounded only by its expiry. Short access + refresh rotation is the standard tradeoff: refresh token rotation means every refresh issues a new refresh token and invalidates the old one, so a stolen refresh token that gets used by both the attacker and the legitimate user creates a detectable conflict (reuse detection) — that's your signal to revoke the whole token family.
- **Storage: httpOnly, Secure, SameSite=Lax/Strict cookie for the refresh token — not localStorage.** localStorage is readable by any JS on the page, so one XSS vulnerability (a dependency, a reflected input, a third-party script) exfiltrates every token instantly with no further exploitation needed. A cookie marked httpOnly is invisible to JS — XSS can still make authenticated requests via the cookie, but can't read/exfiltrate the token itself, which limits impact to the current session rather than a portable stolen credential. The tradeoff this introduces is CSRF, which is why httpOnly cookie + CSRF token (see `cors-csrf-defense`) is the combination that actually covers both attack surfaces — cookie alone is not sufficient. Access tokens used for API calls can live in memory (JS variable, not storage) and get re-fetched via the refresh endpoint on page load.
- **JWTs cannot be revoked — the token is valid until it expires, full stop.** There is no "logout" for a stateless JWT; "logout" only clears the client's copy. If a token needs to be killable before natural expiry (compromised account, admin-forced logout, permission downgrade), you need either (a) a server-side blocklist/deny-list keyed by token `jti` checked on every request — which reintroduces the statefulness JWTs were supposed to avoid — or (b) short expiry + refresh rotation so the compromise window is bounded to one access-token lifetime. Decide which one the system needs *before* building the auth layer; retrofitting a blocklist later means touching every verification path.
- **Never accept `alg: none`, and never let the token dictate its own verification algorithm.** The classic JWT bypass: an attacker sends a token with header `{"alg":"none"}` and no signature, and a library that trusts the header's `alg` field happily "verifies" it. Pin the expected algorithm explicitly in your verify call (e.g., `jwt.decode(token, key, algorithms=["RS256"])`, not reading `alg` from the token itself). The same class of bug applies to RS256-signed tokens verified with the public key passed as an HMAC secret — always fix the algorithm family server-side, don't let client input choose it.
- **Verify `exp`, `iat`, `aud`, and `iss` on every request**, not just signature. A validly-signed token issued for a different service (same signing key, different `aud`) or a clock-skewed `exp` are both real production bugs, not edge cases.
- Rotate signing keys with a `kid` header and a small overlap window — don't force every session to re-auth on rotation.
