Non-negotiables for frontend work, organized by failure mode they prevent. Source: distilled from a 15-principle frontend audit framework (standards-frontend.netlify.app) covering UX, performance, accessibility, and conversion design, adapted into concrete rules for this stack (React/Next.js/TypeScript/Tailwind v4).

**Touch targets.** Every interactive element (button, link, checkbox, form control) gets a minimum hit area of 44×44px (Apple HIG) / 48×48dp (Material), enforce this in the shared Button/Input/IconButton components, not per-call-site, so it can't regress. Visual size can be smaller if padding makes up the difference; what matters is the clickable/tappable area.

**Core Web Vitals.** Target LCP < 2.5s and INP < 200ms on real pages, not just lab Lighthouse runs. Default to Server Components for anything that doesn't need interactivity; push `'use client'` boundaries as low in the tree as possible. Defer non-critical scripts (`next/script` with `strategy="lazyOnload"` or `"afterInteractive"`), and never block LCP on a client-fetched hero image, use `next/image` with `priority` on above-the-fold images only.

**Accessibility (WCAG 2.2 AA).** Text contrast ≥ 4.5:1, large text/UI components ≥ 3:1, check with axe-core or Chrome DevTools' accessibility panel before calling a UI done, don't eyeball it. Target size (SC 2.5.8) is 24×24 CSS px minimum, 44/48px is design guidance (Apple HIG / Material), not the WCAG floor; use it anyway as the shared-component default since it's the stricter, safer bar. Dynamic content (toasts, form errors, cart updates) needs `aria-live` regions so screen readers announce changes; a visual-only state update is a silent failure for assistive tech. Every form input needs a programmatically associated label (`<label htmlFor>` or `aria-labelledby`), not just placeholder text.

**Forms and error prevention.** Use React Hook Form + Zod for a form with several fields or non-trivial validation (frontend-master REACT-15 allows plain controlled state or a server action for simple ones), client-side schema validation catches errors before submit, and the same Zod schema can validate server-side. Never clear a user's input on validation failure; re-render with the error inline next to the field that failed. Payment/card fields get a Luhn check client-side before submit. Keep checkout and signup flows as short as the data actually requires, every optional field is a drop-off point; if you're adding a field, justify it against that cost first.

**Design tokens over magic values.** Colors, spacing, radii, and type scale live in CSS custom properties exposed through Tailwind v4 `@theme` (there is no `tailwind.config`, see frontend-master STYLE-01), typed where possible, never hardcode a hex color or an arbitrary px value in a component when a token exists. Limit the palette to 3-5 semantic colors (primary, secondary, success, danger, neutral) and at most two font families; more than that is a sign the design system needs consolidating, not extending.

**Navigation and layout.** Use an 8px grid for spacing so density reads as intentional rather than arbitrary. Checkout/payment flows should be isolated from site navigation (no header nav leaking the user out mid-purchase), in Next.js, a Route Group with its own layout is the natural mechanism. Filter/search state belongs in the URL (searchParams), not component state alone, so results are shareable and survive a refresh.

**Loading and error feedback.** Every async boundary gets an explicit loading state (`<Suspense>` + skeleton, not a blank screen) and an explicit, specific error state, "Payment failed: card declined" beats "Something went wrong." Silent failures (a failed mutation that just doesn't update the UI) are worse than a visible error; always surface the failure path.

**Trust signals on commerce/content surfaces.** Product/content lists show aggregate ratings when available, use JSON-LD structured data for SEO and rich results, and label outbound/third-party redirects explicitly ("Continue to PayPal") rather than letting the user land on an unfamiliar domain unannounced.

**Motion and reduced-motion.** Respect `prefers-reduced-motion`, wrap animation logic in a `useReducedMotion`-style check (or `MotionConfig reducedMotion="user"` if using the `motion` package) and disable non-essential motion entirely when it's set, not just shorten it; this is the highest-severity motion checkpoint. Small state-change transitions run ~150-300ms, larger/layout transitions up to ~500ms, longer reads as sluggish, shorter as jarring. Animate only `transform` and `opacity` (compositor-only), animating `width`/`height`/`top`/`left`/`box-shadow` etc. forces layout/paint and is a performance regression, not a style choice. Any auto-playing motion (carousel, video background, looping animation) that runs longer than 5s needs a visible pause/stop control (WCAG 2.2.2), unpausable auto-play is a hard accessibility fail, not a design nice-to-have. Motion is explicitly the lowest-weighted principle in the audit framework (3/100, vs. 10 for performance and accessibility), don't let animation polish eat time budgeted for higher-weight work.

**i18n-readiness.** Use CSS logical properties (`margin-inline-start` over `margin-left`) in shared components so RTL locales don't require a parallel stylesheet. Keep user-facing strings in typed dictionaries/translation files from the start rather than retrofitting, bilingual projects in particular should never hardcode an English string in a component.

**Verification before calling UI work done.** A passing build/typecheck is necessary but not sufficient, run the `visual-qa` skill against the actual rendered app for any non-trivial UI change. Don't claim a UI change is correct from reading the diff alone.
