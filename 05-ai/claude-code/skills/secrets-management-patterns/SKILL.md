description: Use when adding new environment variables/API keys to a project, setting up CI/CD secrets, reviewing logging code near auth flows, or before a git push/commit that touches config files. Trigger on ".env" changes, new third-party API integrations, or "did I just commit a secret" concerns.
---

Handling credentials, API keys, and tokens across a codebase's full lifecycle — not just "don't hardcode it," which everyone already knows and does anyway under deadline pressure.

Non-negotiables:

- **`.env.example` is always committed with every key name and a placeholder/description; `.env` is always gitignored, no exceptions for "just this once" or a demo project.** The failure mode isn't usually someone hardcoding a key — it's `.env` getting committed on day one before `.gitignore` is set up, then living in git history forever even after a later commit deletes it. Check `.gitignore` covers `.env*` (except `.env.example`) at project init, not after the first leak.
- **Design for rotation from the start, not as an incident-response afterthought.** A hardcoded assumption that "there's one API key" breaks the moment a key needs rotating without downtime — you need either dual-key support during a rotation window (accept both old and new for a grace period) or a config layer that can hot-reload from a secrets manager without a redeploy. Retrofitting rotation support into a system built assuming static keys is a multi-day job that a day-one decision avoids. This matters most for anything a client's ex-employee, a leaked CI log, or a compromised dependency could have seen.
- **Never-log-this list, enforced at the logging layer, not by developer memory:** raw `Authorization`/cookie headers, full request/response bodies on any auth endpoint (login, token refresh, password reset), API keys/secrets even in error messages ("failed to connect with key sk-abc123..." is a real leak pattern), full JWTs (log the `sub`/`jti` claim instead), webhook signing secrets, DB connection strings. Sanitize at the logging middleware/interceptor level (a redaction filter on known header/field names) so a new endpoint doesn't reintroduce the leak by omission. Sentry/Datadog/CloudWatch retention makes a logged secret a standing liability, not a one-time mistake — it sits there until someone rotates it.
- **CI/CD build logs leak secrets more than people expect.** A masked/secret env var in GitHub Actions/GitLab CI is only masked in the *known* literal form — if a script echoes it after transformation (base64-encoded, JSON-stringified, concatenated into a URL), the mask doesn't catch it and it prints in plaintext to a log every team member (and sometimes the public, on OSS repos with misconfigured fork PR workflows) can read. Never `echo`/`print` a secret var even for "debugging," never pass secrets as CLI args (visible in process listings and shell history), and check that fork-triggered CI runs don't get access to repo secrets at all — that's a classic way an external PR exfiltrates production keys.
- **Pre-commit hooks (gitleaks, detect-secrets, truffleHog) catch what code review misses** — a reviewer skimming a 40-file diff will not spot one new `AKIA...` string. Wire a secret scanner into pre-commit, not just CI, so the leak never reaches a shared branch or a fork's CI logs in the first place — a secret caught in CI has already left the developer's machine. If a secret does get committed, rotating it is mandatory even after a history rewrite; git history rewrites don't un-leak a key that was ever pushed.
