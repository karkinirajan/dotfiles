Non-negotiables and the failure modes behind them.

**Application factory pattern.** A module-level `app = Flask(__name__)` with extensions initialized against it at import time (`db = SQLAlchemy(app)`) is the single most common source of circular imports in Flask codebases: `models.py` needs `app` to init `db`, blueprints need `models`, `app.py` needs blueprints — there's no import order that works once the app grows past a couple files. The fix is `create_app()`: a function that constructs the `Flask` instance, calls `.init_app(app)` on every extension, registers blueprints, and returns `app`. This also solves a second problem for free — testing needs a fresh app instance per test (different config, isolated DB), and multiple app instances in one process (e.g., a Celery worker importing the app differently than the web process) become normal instead of impossible. If you inherit a codebase with the global-`app` pattern and it's causing import errors, migrating to a factory is worth the churn; don't just add another circular-import workaround.

**Extension init pattern.** Every well-behaved Flask extension supports deferred init: instantiate at module level with no app (`db = SQLAlchemy()`), then `db.init_app(app)` inside the factory. This is what makes the factory pattern possible — extensions must not require the app at construction time. If a third-party or internal "extension" only supports eager `Extension(app)`, wrap it or find the deferred-init alternative rather than reintroducing a module-level app dependency.

**Blueprint organization.** One blueprint per domain area (`auth`, `api`, `admin`), each with its own `routes.py`/`models.py` if the domain is large enough — not one blueprint per file for its own sake. Register blueprints in the factory, not scattered `import`-time side effects. URL prefixes belong at registration (`app.register_blueprint(api_bp, url_prefix="/api/v1")`), not hardcoded into every route string, so versioning or mounting the same blueprint twice doesn't require touching every handler.

**When Flask is the right call.** Choose Flask for small services, internal tools, webhook receivers, or anything where you want explicit control over every piece (routing, serialization, auth) without a batteries-included ORM/admin/auth stack — it's the right size when the alternative frameworks bring more machinery than the problem needs. Choose FastAPI over Flask for anything async-heavy (high-concurrency I/O-bound APIs, streaming, WebSockets) or where automatic OpenAPI/Pydantic validation saves real time — Flask's request validation is manual by default. Choose Django/DRF over Flask when the service needs a real admin panel, a mature ORM with migrations, or built-in auth/permissions out of the box — rebuilding those in Flask via extensions (Flask-Admin, Flask-Migrate, Flask-Login) is a legitimate choice but a slower one; don't default to Flask on a new service just because it's familiar if the requirements are actually Django-shaped.
