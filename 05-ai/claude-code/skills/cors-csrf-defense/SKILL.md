Configuring cross-origin request handling and CSRF defense for a production API. The two are frequently confused and the confusion causes real vulnerabilities.

Non-negotiables:

- **CORS is not a server-side security boundary — it's a browser-enforced restriction on the client.** Your API is exactly as reachable from `curl`, Postman, a server-to-server call, or a malicious script running outside a browser sandbox with CORS misconfigured as with it configured perfectly. `Access-Control-Allow-Origin: *` does not mean "anyone can call this endpoint" in some new way — anyone could already call it; CORS only controls whether a *browser*, on behalf of a page from a different origin, is allowed to let JS read the response. Don't add auth logic that assumes CORS is blocking unauthorized access — it never was. The actual boundary is authentication + authorization on the server.
- **"Works in Postman, fails in the browser" is almost always a missing/misconfigured preflight response, not a broken endpoint.** Any cross-origin request with a non-simple method (PUT/DELETE/PATCH), a custom header (`Authorization`, `X-CSRF-Token`), or a JSON content-type triggers a browser preflight `OPTIONS` request first. If your server doesn't respond to `OPTIONS` with matching `Access-Control-Allow-Methods`/`-Headers`/`-Origin` (and `-Credentials: true` if cookies are involved), the browser never sends the real request — Postman skips preflight entirely because it isn't a browser, which is why it "works" there and nowhere else. Debug by checking the Network tab for the `OPTIONS` call and its response headers, not the failed follow-up request.
- **`Access-Control-Allow-Origin: *` is incompatible with `Access-Control-Allow-Credentials: true`** — browsers reject the combination outright. If cookies or `Authorization` headers need to cross origins, you must echo back a specific validated origin from an allowlist, never a wildcard.
- **CSRF token pattern choice:** double-submit cookie (a token set in a readable cookie, echoed back in a header/body field, compared server-side — no server-side session storage needed but weaker against subdomain cookie injection) vs synchronizer token (token stored server-side tied to the session, compared against a hidden form field/header — stronger, needs session state). For an API with httpOnly session cookies, synchronizer-style (token issued at login, stored server-side or signed, required on every mutating request) is the safer default; double-submit is fine for stateless/JWT-cookie setups where there's no session store to tie the token to.
- **`SameSite=Lax` or `Strict` on the session cookie is defense-in-depth, not a CSRF token replacement.** `Lax` still allows top-level navigation GETs to carry cookies (so a GET-triggered state change is still exploitable), and any cross-origin subdomain or misconfigured proxy can create gaps. Ship both: SameSite cookie attribute AND explicit CSRF token validation on state-changing (POST/PUT/PATCH/DELETE) requests. Relying on SameSite alone is a common "we're modern, we don't need CSRF tokens" mistake that breaks the moment there's a legitimate cross-site POST use case (widget embed, webhook-triggered form) that forces `SameSite=None`.
