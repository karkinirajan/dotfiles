Non-negotiables and the failure modes behind them.

**v1-to-v2 breaking changes worth knowing on sight.** `@validator`/`@root_validator` are deprecated shims in v2 — use `@field_validator` and `@model_validator`. `class Config:` inner class is replaced by `model_config = ConfigDict(...)` as a class attribute; the two don't merge, so a half-migrated model silently ignores whichever style isn't the one v2 reads. `.dict()`/`.json()` are deprecated aliases for `.model_dump()`/`.model_dump_json()` — still work but signal unmigrated code, and `.model_dump_json()` handles more types correctly (e.g., datetime) without a custom encoder. `parse_obj`/`parse_raw` → `model_validate`/`model_validate_json`. Validation is stricter by default in v2 — a str `"123"` no longer silently coerces to an int field the way v1's lax mode did; if you're seeing new `ValidationError`s after a v1→v2 upgrade on previously-working data, this is almost always why, and the fix is fixing the data/type, not reaching for `Field(strict=False)` as a reflex.

**Validator ordering.** `field_validator(..., mode="before")` runs before Pydantic's own type coercion — use it to accept multiple input shapes (e.g., a comma string or a list) and normalize to one type. `mode="after"` (the default) runs on the already-coerced, already-typed value — use it for range/format checks that assume the type is correct. `model_validator(mode="before")` receives the raw input dict before any field validation — the only place to rename/restructure keys or handle a payload shape that doesn't map 1:1 to fields. `model_validator(mode="after")` receives the constructed model instance — use it for cross-field invariants (`end_date > start_date`), and note it runs after every individual field validator, so a field-level error on one field will prevent the model-level check from running against invalid data. Getting before/after backwards is the most common bug here: putting a cross-field check in a `mode="before"` model validator means you're inspecting a raw, possibly not-yet-typed dict, not the values you think you're comparing.

**BaseSettings for config.** Lives in `pydantic-settings` now, not core `pydantic` — a common v2 upgrade miss (`ImportError` or, worse, a silently different class if both are installed). Precedence, highest to lowest: explicit constructor kwargs > environment variables > `.env` file > field defaults — so a value that "isn't picking up" from `.env` is often actually being overridden by a real env var already set in the shell/container, which wins by design. `env_file=".env"` in `model_config` only loads a file if one exists at that path relative to CWD at runtime — in Docker, that's the container's working directory, not the repo root on disk, a frequent source of "works locally, empty in prod." Nested config (`DATABASE_URL` vs `database__url` for nested models) needs `env_nested_delimiter` set explicitly or nested settings silently stay at their defaults. Never let `BaseSettings` defaults mask a genuinely required prod value — no default (or a default that fails fast) on secrets, so a missing env var is a startup crash, not a quiet fallback to a dev value in production.

**Discriminated unions.** For polymorphic API payloads (a `type` field selecting one of several shapes), use `Field(discriminator="type")` with a `Literal["a"]`/`Literal["b"]` field on each member model, not a bare `Union[ModelA, ModelB]`. A bare union validates against each member in order and returns the first match or a confusing multi-model error list — slow and prone to silently matching the wrong shape when one model's fields are a subset of another's. The discriminated form does an O(1) dispatch on the tag field and gives a precise error naming the exact variant that failed, which matters once you have more than two or three shapes.
