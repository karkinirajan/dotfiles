Non-negotiables and the failure modes behind them.

**App boundaries.** A Django "app" should map to a bounded domain concept (`billing`, `notifications`, `accounts`), not a technical layer (`views`, `models`) or a single feature ticket. Split when two areas start needing different deployment cadences, different owners, or when one app's `models.py` exceeds ~500 lines with unrelated concerns. Don't split preemptively — a two-model app with no independent lifecycle is just import indirection. Circular imports between apps (`billing` importing `accounts.models`, `accounts` importing `billing.models`) are a boundary-design smell, not a Python problem to route around with local imports; fix the boundary.

**Serializer vs model validation.** Model `clean()`/`full_clean()` and DB constraints enforce data integrity regardless of entry point (admin, shell, management command, API) — put invariants that must always hold there. Serializer `validate_<field>`/`validate()` enforces request-shape and cross-field rules specific to *this* API contract (e.g., "email required only on signup, not on profile update"). Relying on serializer validation alone means the admin panel and `Model.objects.create()` in a script bypass it entirely — a recurring source of bad data that "shouldn't be possible."

**ViewSet vs APIView.** `ModelViewSet` is right when the endpoint is genuinely CRUD over one model with router-standard URLs — you get list/create/retrieve/update/destroy for free and consistent pagination/filtering wiring. The moment an action doesn't map to CRUD (a multi-step workflow, an endpoint touching multiple models, custom bulk logic), forcing it into a viewset via `@action` decorators past 2-3 custom actions is a sign it should be a plain `APIView` — you're fighting the abstraction to save router boilerplate you don't actually need.

**Signal discipline.** `post_save`/`pre_delete` signals decouple the trigger from the effect at the cost of making the effect invisible at the call site — a bug six months later means grepping for "does anything listen on this model" instead of reading the function. They're legitimate for genuinely cross-cutting, optional concerns (search index sync, audit logging, cache invalidation) where the sender shouldn't need to know the receiver exists. They're the wrong tool for anything that's core business logic of the save operation itself (e.g., "creating an order must decrement stock") — that belongs in a service function called explicitly, so it's traceable, testable without signal registration side effects, and doesn't silently fire during bulk operations (`bulk_create`/`bulk_update` skip signals entirely — a common prod surprise).

**Query efficiency as default habit.** Any serializer field or template access crossing a FK/M2M is an N+1 candidate — reach for `select_related` (FK/O2O, SQL join) and `prefetch_related` (M2M/reverse FK, separate query + Python join) at the queryset definition in the view/manager, not as a later optimization pass. Check with `django-debug-toolbar` or `.explain()` before calling a list endpoint done — "it works" on a 3-row dev DB hides O(n) queries that surface as timeouts at 10k rows in prod.
