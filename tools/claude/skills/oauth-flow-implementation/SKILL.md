Implementing OAuth2 authorization code flow for third-party login. This is a client-server dance with a browser in the middle that leaks credentials if any step moves server logic into that browser.

Non-negotiables:

- **PKCE always, even for confidential (server-side) clients.** The old advice — "PKCE is only for public/mobile clients without a secret" — is dead; OAuth 2.1 mandates PKCE for all client types. It defends against authorization code interception (a code leaked via referrer header, browser history, or a malicious app on the same device) that a client secret alone doesn't stop. Generate `code_verifier` server-side, send `code_challenge` (S256, never `plain`) in the authorize request, send the verifier in the token exchange. Skipping this because "we have a client secret" is the single most common gap in hand-rolled implementations.
- **`state` parameter is CSRF protection for the login flow itself, not optional.** Without it, an attacker can initiate their own OAuth flow, capture the callback, and trick a victim into completing login as the attacker (session fixation via login CSRF). Generate a random value, store it server-side (session or signed cookie) before redirecting, verify exact match on callback before touching the code. Don't reuse `state` as a general-purpose redirect target — that opens an open-redirect vector.
- **Token exchange happens server-side only.** The authorization code goes from the provider to your backend's callback endpoint; the code-for-token POST (with `client_secret`) happens from your server to the provider, never from the browser. If a client secret ever appears in frontend JS, a network tab, or a mobile app binary, treat it as already compromised — rotate it.
- **Redirect URI validation must be exact-match, not prefix-match.** Providers validate what you registered, but your own callback handler (if it does any internal routing based on a `redirect_uri` or `next` query param) must also exact-match against an allowlist. Prefix matching (`startswith('https://app.example.com')`) is bypassable with `https://app.example.com.attacker.com` or a path like `/callback/../../attacker-controlled`. This is how open redirects turn into full account takeover via code/token theft.
- **Don't build one unified provider abstraction before checking the real deltas.** Google returns a verified `email` claim and supports `prompt=consent` for refresh tokens on re-consent; GitHub's `/user` endpoint requires a separate call for email if the primary is private, and email can be null; Microsoft's tenant-specific vs `common` endpoint changes token validation (`iss` claim varies by tenant). A naive `provider.getUser()` interface that assumes email presence and shape will break silently on GitHub users with private emails — fetch `/user/emails` explicitly and filter for `primary && verified`.
- **Validate `id_token` (OIDC) signature and claims server-side** — `aud` matches your client ID, `iss` matches the expected provider, `exp` not passed. Never trust an unverified decoded JWT from a provider redirect.
