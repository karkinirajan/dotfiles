Non-negotiables and the failure modes behind them.

**Session / Unit-of-Work lifecycle.** A `Session` is a transaction boundary and an identity map, not a connection you hold open casually. `DetachedInstanceError` — the single most common SQLAlchemy bug — happens when you access a lazy-loaded attribute on an object after its `Session` closed (request ended, `with Session() as s:` block exited). The fix is never "catch the exception and re-fetch" as a pattern; it's either load what you need before the session closes (eager loading — see below), or keep the object attached for as long as attribute access is needed and scope the session to that lifetime (one session per request in a web app, via a dependency/middleware, not one global session reused across requests — that causes a different bug: stale identity-map data and cross-request state leakage). Never share one `Session` across threads or async tasks concurrently; it isn't thread-safe. Call `session.commit()` explicitly at the unit-of-work boundary — don't rely on autocommit-like patterns or commit deep inside a helper function, or you lose the ability to roll back a multi-step operation atomically.

**Relationship loading strategy.** The default `lazy="select"` fires one query per accessed relationship per row — fine for a single object, an N+1 footgun the instant you iterate a list and touch a relationship (`for order in orders: order.customer.name`). `joinedload()` (SQL JOIN, one query) is right for a to-one relationship you always need — it can duplicate parent rows when combined with a collection join, so don't stack it on a one-to-many without also using `contains_eager` correctly. `selectinload()` (separate `WHERE id IN (...)` query) is usually the better default for to-many relationships — no row duplication, scales fine, and is easy to reason about; prefer it over `joinedload` for collections unless profiling says otherwise. Set the strategy at the query (`.options(selectinload(Order.items))`), not as a blanket `lazy="joined"` on the model — a relationship that's cheap in one query path is wasteful eager-loaded in another.

**Alembic migrations.** `alembic revision --autogenerate` produces a *draft*, not a migration — it misses server-side defaults changes, check constraints, and can generate a full table rewrite for a trivial column reorder in some DBs. Always read the generated diff before running it: verify index/constraint names it invents are sane (not `ix_table_col_col_col`), verify it doesn't drop and recreate a column when a simple `ALTER COLUMN TYPE` would do, and add data migrations by hand (autogenerate never writes data-moving code). On a table with meaningful row count, check whether the generated `ALTER TABLE` takes a lock that blocks writes in your DB engine, and split into safe steps (add nullable column → backfill in batches → add NOT NULL constraint) instead of one blocking migration.

**Async SQLAlchemy.** `AsyncSession` and sync `Session` are not interchangeable and don't mix in the same call path — a sync engine/session called from an async route blocks the event loop exactly like any other sync I/O; an `AsyncSession` requires `await` on every DB-touching call (`await session.execute(...)`, `await session.commit()`) and an async driver (`asyncpg`, not `psycopg2`) in the connection URL. Lazy-load access on a relationship in async code raises `MissingGreenlet` unless you've eagerly loaded it or used `AsyncAttrs` — this is the async-world equivalent of `DetachedInstanceError` and the fix is the same: load what you need up front via `selectinload`/`joinedload` in the query, don't rely on implicit lazy access after the fact.
